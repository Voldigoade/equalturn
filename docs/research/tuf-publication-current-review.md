# TUF publication and Rust client review

**Checked:** 20 October 2026<br>
**Scope:** TUF specification, publisher and signer lifecycle, the staging interoperability incident, and Equalturn's current production trust boundary.

## Verified upstream facts

- The [TUF specification v1.0.37](https://theupdateframework.github.io/specification/v1.0.37/) defines pinned-root bootstrap, version-by-version root rotation, threshold signatures, role metadata, expiry, and consistent repository metadata. The client must start from independently trusted root bytes; fetching a root and accepting it from the same unauthenticated repository is not bootstrap.
- The [TUF-on-CI changelog](https://github.com/theupdateframework/tuf-on-ci/blob/main/docs/CHANGELOG.md) lists v0.21.0 as its latest release at review. Its [repository maintenance guide](https://github.com/theupdateframework/tuf-on-ci/blob/main/docs/REPOSITORY-MAINTENANCE.md) says to initialize a TUF-on-CI repository with `tuf-on-ci-delegate sign/init`, then use its signing-event workflow. The [signer manual](https://github.com/theupdateframework/tuf-on-ci/blob/main/docs/SIGNER-MANUAL.md) describes local signer review and signatures recorded in signing-event pull requests.
- TUF-on-CI's [online-signing guide](https://github.com/theupdateframework/tuf-on-ci/blob/main/docs/ONLINE-SIGNING-SETUP.md) lists AWS KMS, Google Cloud KMS, and Azure Key Vault integrations for snapshot and timestamp. Sigstore is marked experimental and the guide warns it is not supported by all TUF client libraries. The selected publisher workflow supports per-job `id-token`, repository contents, pull-request, and workflow-dispatch permissions. Its repository template pins upstream actions to immutable full commit SHAs.
- Equalturn uses `sigstore-tuf` 0.15.0 for the TUF client state machine. The repository transport is Equalturn-owned: it disables redirects, validates the HTTPS origin, applies explicit timeouts and streamed response bounds, and fetches the fixed `registry-v3.json` target. The client accepts standard TUF public key metadata. It does not implement the staging TAP-18 `sigstore-oidc` key type.
- The production publisher repository `Voldigoade/equalturn-registry` is public and based on the upstream TUF-on-CI template. Its default branch is `main`; as of review, it has no Equalturn root, role keys, metadata, registry target, Pages configuration for the Equalturn feed, or configured online signer. No production signer or cloud account was provisioned.

## Staging interoperability incident

The first TUF-on-CI staging attempt started from standard-key metadata produced externally by `tuftool`, then passed that repository state to the TUF-on-CI build action. The actual action run failed while reading the repository's TUF-on-CI expiry configuration: the externally generated metadata did not contain the expected `x-tuf-on-ci-expiry-period` field. This was a publisher lifecycle/configuration mismatch, not a failure of standard TUF signatures.

Staging was then published as fixed-content Pages data with standard TUF keys, so the selected Equalturn Rust client could exercise a real pinned-root update. The staging HTTPS smoke now succeeds, but the static workflow does not renew metadata. A previous Sigstore/OIDC TUF-on-CI staging state used TAP-18 OIDC keys and was rejected by the Rust verifier; it is retained only as public historical evidence. The two staging findings are independent: use of an experimental signature type caused the client incompatibility, while external metadata creation caused the missing TUF-on-CI expiry configuration.

## Decision

Keep TUF as the sole metadata and target authentication protocol. Keep `sigstore-tuf` as the Rust verifier and TUF-on-CI v0.21.0 as the publisher. Use the TUF-on-CI `sign/init` path end to end for production so its expiry configuration and renewal workflow are created by the same mature tool that consumes them. Use standard TUF key types already accepted by Equalturn; do not use TAP-18/OIDC signatures for root or targets, do not hand-edit TUF-on-CI extension metadata, and do not create an Equalturn signing implementation.

Root and targets remain human-controlled roles and are never placed in CI. Snapshot and timestamp may use separate OIDC-federated KMS identities after the owner explicitly selects/provisions a provider and the repository/workflow identity is narrowly restricted. Do not use long-lived cloud credentials or static role private keys in GitHub Secrets. The earlier staging-only OIDC and noreply approvals do not authorize production key custody or infrastructure.

The production client remains fail-closed until the production root is initialized through TUF-on-CI, independently verified by the existing Rust client, and its exact public bytes and digest are embedded in an Equalturn release. Production trust must never fall back to staging. Public registry signatures prove publisher authorization and byte integrity, not that an indicator is true, complete, current, or safe to enforce.

## Workflow review and limitations

The current production `online-sign.yml` has empty workflow-level permissions. Its online-sign job requests `id-token: write`, `contents: write`, and `actions: write` for OIDC identity, metadata updates, and publishing dispatch; the template provides a GitHub App alternative for repository writes. Its signing-event job requests `contents: write`, `pull-requests: write`, and `actions: write` for signing branches/PR lifecycle; a separate status issue job receives only `issues: write` and `contents: read`. The actual TUF-on-CI actions and GitHub App token action are SHA-pinned. These are necessary upstream capabilities, but their effective security still depends on workflow triggers, branch/environment settings, OIDC claims, signing key scope, and maintainer account security.

The current registry publication repository's README confirms no root, key, metadata, or target exists. Its authenticated GitHub settings UI was inspected read-only on 20 October 2026: Pages is disabled, no environment or branch ruleset exists, default `GITHUB_TOKEN` permissions are read-only with PR creation disabled, but the Actions allowlist allows all actions and does not require full-SHA pins. Secret scanning and push protection are enabled; dependency graph/Dependabot alerts are off. Equalturn's source repository has similarly permissive action allowlisting/SHA settings and no branch ruleset, but dependency graph/alerts, secret scanning, push protection, and private vulnerability reporting are enabled. The production policy records what should change before signing. No setting was modified and no production key/provider setup is inferred from repository write access.

Context7 was queried on 20 October 2026 for TUF-on-CI and `sigstore-tuf`; it did not return exact library entries for either. It returned upstream Python-TUF and TUF augmentation proposal documentation. The current TUF-on-CI manuals, template/workflow sources, versioned [`sigstore-tuf` docs](https://docs.rs/sigstore-tuf/0.15.0/sigstore_tuf/), pinned crate source, TUF specification, and actual staging workflow result were used instead. This is a Context7 index limitation, not evidence that the reviewed projects are unmaintained.
