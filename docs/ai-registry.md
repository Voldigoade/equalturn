# AI ecosystem and registry design

**Research date:** 19 October 2026. Registry v3 is a researched catalogue for ecosystem discovery. It contains 129 provider/product/surface records, 132 dated source records, and 58 structured indicators migrated from the audited v2 snapshot. V3 adds explicit platform/surface, provenance date, confidence, actionability, false-positive risk, lifecycle, and limitations fields. Migrated indicators deliberately use `low` confidence, `research_only` actionability, `unknown` platform/risk/lifecycle until those classifications receive an indicator-level review. The registry is incomplete and is not an enforcement policy or an implementation of AI blocking. The application does not load it. See the [v2 quality audit](research/registry-quality-audit.md) and [v3 migration notes](research/registry-schema-v3.md).

## Method and coverage

Research started from the 18 requested capability categories rather than a provider blacklist. The canonical snapshot in `registry/registry-v3.json` contains 129 provider/product/surface records across all 18 categories, 132 dated source records, and 58 structured indicator instances. A local audit confirmed that every indicator's `source_id` resolves to a source in its own entry. This is a broad research sample, not 129 items with actionable controls: even a documented indicator may be ambiguous, configurable, shared with unrelated functions, or unsuitable for blocking. Each source record carries a URL, check date, and source-specific assessment. First-party product/API documentation and upstream project repositories provide provenance; where a value or scope was not explicit, the record preserves a written research assessment without inventing a structured indicator.

**Source ID scope:** `source-1`, `source-2`, and similar labels are local to a registry entry. They intentionally repeat across different entries; the current snapshot has 132 source records but only two distinct ID strings globally. Resolve an indicator's `source_id` only against the `sources` array in that same entry. These labels are not stable, globally addressable source IDs and must not be used as cross-entry keys. A future registry revision may adopt globally unique IDs only with an explicit migration.

The original 30-record sample remains in `registry/registry-v1.json`, described by `registry/schema-v1.schema.json`. Those v1 artifacts are unchanged. The expanded v2 snapshot and schema remain available for migration/audit history. The canonical current dataset is `registry/registry-v3.json`, described by `registry/schema-v3.schema.json`; `tools/migrate_registry_v2_to_v3.py` performs a deterministic, fail-closed v2 migration. The quality audit split Mistral Vibe Code and MiniMax Code from broader chat/agent records, corrected two hosted-chat tags, removed an unsupported generic TGI port, and refreshed product status/provenance where evidence supported it. Neither version estimates the full market or provides a completeness score. Product names, endpoints, ownership, and routing capabilities change quickly; this snapshot was checked on 19 October 2026.

## Why a manually curated blacklist is insufficient

An endpoint can be an official provider API, an aggregator, a user-configured proxy, a local model, an arbitrary server, or a shared cloud domain. A brand/domain list cannot identify semantic model usage across encrypted HTTPS, locally embedded runtimes, self-hosted services, custom ports, containers, or remote systems. Conversely, blocking a broad cloud hostname can break unrelated development work. V2 is a research catalogue, not an oracle or deny list; its records do not establish which product or model a participant used.

V3 indicators contain an evidence kind and normalized value, platform and surface scope, source reference and verification date, confidence, actionability, false-positive risk, lifecycle, scope, and limitations. These are research classifications, not runtime decisions: even `blocking_candidate` is only a candidate requiring separate policy, platform feasibility, review, and user consent. `unsafe_to_block` means the indicator is unsuitable as a block key; it does not mean the product is safe or permitted. The v2 quality audit removed the TGI example port `8080` because it is generic and not a product identity. Remaining local listeners are explicitly represented as loopback ports, and migrated indicators remain `research_only` until individually reviewed. Unknown applications and unlisted providers must remain unknown rather than being silently treated as clean.

## Schema and update lifecycle

`registry/schema-v1.schema.json` describes the unchanged v1 sample; `registry/schema-v2.schema.json` preserves the v2 migration source; `registry/schema-v3.schema.json` describes the current registry. V3 separates:

- stable IDs for provider and product records;
- the 18 descriptive capability categories and client surfaces, which do not guarantee that a surface is detectable or blockable;
- source records with URL, `checked_on`, and source-specific `indicator_assessment`;
- typed, normalized indicators with provenance and explicit safety classifications;
- optional product relationships such as `routes_to`, `provided_by`, or `integrates_with` (the current expansion leaves them empty where a specific relationship was not established);
- research status (`observed`, `unknown`, `deprecated`, `archived`, or `disputed`).

V3 retains the product-level surface vocabulary and adds `unknown` only for indicator-level surface where the v2 evidence could not establish one. Indicator platform is likewise `unknown` after migration because v2 recorded no platform. `self-hosted` is a deployment mode, not a surface; the data keeps that distinction in category/source assessment text rather than pretending it is an access surface. Confidence means evidence confidence in the indicator claim, not probability of AI use; `high` requires direct, specific, first-party or upstream evidence, `medium` means credible but scoped or indirect evidence, and `low` means weak, ambiguous, or newly migrated evidence. False-positive risk is the chance an observation matches unrelated or permitted activity (`unknown` is not treated as low). Actionability options are `research_only`, `advisory`, `detection_candidate`, `blocking_candidate`, and `unsafe_to_block`; definitions and migration rationale are in the [v3 migration notes](research/registry-schema-v3.md).

Keep the dataset separate from enforcement code. Add a record only with a first-party or independently credible source and a check date. Add a structured indicator only when its specific value and scope are supported; record shared/region-specific hosts, configurable endpoints, and false-positive or coverage limits in the source assessment. Retain archived or deprecated entries with status and migration notes rather than silently deleting history.

The v2 JSON Schema describes the migration source. `tools/validate_registry_v3.py` applies the v3 Draft 2020-12 schema (including format checks) to the current target; `tools/validate_registry.py` remains the dependency-free validator for the historical v2 source. The Stage 9 semantic validator will additionally enforce cross-record relationships, normalized syntax, date/provenance consistency, canonical ordering, and contradictory safety classifications. Neither a schema nor validator can prove that a cited page supports a claim or that a product was actually used; human review remains required. Install the pinned schema-validation dependency with `python3 -m pip install -r requirements-registry.txt` before running the v3 validator.

The current application does not consume or update this registry. A future independent-update design may publish versioned research artifacts with signed metadata. TUF is a suitable design family for repository roles, expiration, rollback, and freeze protection; use a maintained implementation and a documented offline root-key ceremony rather than inventing signatures. Any future client should pin trusted root metadata, report expired/invalid data clearly, and never silently change an active session’s registry. No live registry update path, signature verification, or remotely downloaded enforcement policy is implemented here.
