# Independent Milestone 1 security review

**Reviewed:** 19 October 2026 against `226c531fd4724a9fc726868055f43d946df381ce`.

This review examined the protocol, local persistence, relay transactions, report verifier, privacy boundaries, and attacker-controlled resource bounds as a security-sensitive implementation. Findings below describe code at the reviewed commit; remediations are tracked by the Milestone 1.5 stages. A cryptographically valid event authenticates a key's claim. It does not establish that a local client reported reality honestly or completely.

## Findings

| ID | Severity | Finding | Status / owner |
| --- | --- | --- | --- |
| M1-SEC-01 | Moderate | Windows participant identity files contain the raw 32-byte Ed25519 seed. Windows currently relies on inherited filesystem ACLs and does not validate them. Anyone who can read that file can impersonate the session participant. | Fixed in Stage 2 with current-user DPAPI, a versioned bound envelope, no plaintext fallback, and real Windows CI coverage. Legacy plaintext migration is explicit and only occurs for the exact legacy format. |
| M1-SEC-02 | Moderate | Unix participant-key loading checks `symlink_metadata` and permissions, then opens the path separately. The final-component check/open sequence is raceable; directory ownership is not checked; failed writes can leave a partial `create_new` file that prevents retry. | Fixed in Stage 3 with descriptor-relative no-follow operations, owner/mode checks, race-safe creation, and durability. Root and same-user code remain outside this protection. |
| M1-SEC-03 | Moderate | Relay identity persistence checked the final file but not the parent directory's ownership/mode, had a check/open race, did not sync the parent after creation, and a partial `read_exact` failure returned before explicitly zeroizing the stack seed buffer. | Fixed in Milestone 1.5 Stage 4: Unix parent and key-file checks are descriptor-relative, key publication is atomic and no-replace, directory durability is requested, and seed buffers are zeroized on all read paths. Windows opens the final file without following reparse points, uses flushed temporary-file publication, and relies on the inherited parent DACL. See [relay key storage](relay-key-storage.md). |
| M1-SEC-04 | Low | `SigningIdentity::seed_bytes()` exposed a plain `[u8; 32]` copy. Invitation and database credential values could also be retained in ordinary request/configuration strings or exposed by derived diagnostics. | Fixed in Stage 5: seed import/export uses a non-cloneable, non-debug, non-serializable zeroizing wrapper; invitation codes use zeroizing validated storage and redacted request `Debug`; HTTP request buffers are zeroizing owners; relay configuration owns its database URL in a private zeroizing string and redacts `Debug`. See [secret lifecycle](secret-lifecycle.md). This does not guarantee erasure of compiler/register/framework/OS copies. |
| M1-SEC-05 | Moderate | `tools/validate_registry.py` confirms the schema's Draft 2020-12 declaration but does not run a JSON Schema implementation against the instance. Its hand-written checks can drift from the schema. | Replace with a real Draft 2020-12 validation path and semantic diagnostics in the registry validator checkpoint. |
| M1-SEC-06 | Moderate | `equalturn report verify` checked the pathname's length and then used an unbounded `fs::read`. A concurrent replacement/growth could exceed the report cap between those operations. | Fixed in this review checkpoint: open once, inspect the opened file, and read at most `limit + 1` bytes. Unit tests cover exact-limit acceptance and over-limit rejection. |

No high-severity protocol, relay-membership, or report-verification defect was confirmed in the reviewed paths. Findings 01–04 have been remediated in Milestone 1.5 Stages 2–5; M1-SEC-05 remains scheduled for the semantic registry validator stage. These remediations do not change the stated trust boundary or make participant-controlled devices trustworthy.

## Reviewed controls retained

- Participant events, reconnect challenges, heartbeats, relay receipts/notices, and session manifests use separate domain-separated fixed binary encodings. The wire JSON serialization is not treated as signable bytes. Golden vectors exist for the event encoding; Ed25519 verification uses the library's strict verifier.
- Participant keys are session-scoped and bound in the local key envelope to session, participant, and local-store identifiers. Unix key files use owner-only descriptor-relative checks; Windows files use current-user DPAPI. Key lifecycle limitations are documented separately.
- Event admission validates protocol version, IDs, payload bounds, participant membership, signature, sequence, previous hash, event uniqueness, and session capacity inside PostgreSQL transactions. Duplicate identical submissions return the existing receipt; conflicting reuse is rejected.
- Invitations have high entropy, are stored relay-side as a verifier, expire, are limited by participant/session lifecycle and join count, and have a bounded in-memory attempt limiter. Reconnect uses a short-lived random one-use challenge and connection generations to make replacement deterministic.
- HTTP bodies and WebSocket frames are capped at 32 KiB; per-session participants/events/evidence and live connection/fan-out resources have explicit limits. Reports have a 64 MiB parser cap and bounded item counts. The report CLI read cap was made race-resistant in this checkpoint.
- The report verifier checks participant keys, event signatures/chains, receipt/notice signatures and matching, manifest heads, ordering, duplicates, and gaps. It labels included-evidence consistency separately from relay identity anchoring and never emits a cheating verdict.
- Application evidence and structured logs do not include peer transport IPs, invitation codes, private seeds, request bodies, command lines, database passwords, or arbitrary local inventories. CLI arguments and raw transport buffers remain OS/framework-visible during use; this code does not log or persist them. The relay operator and infrastructure can still observe or retain transport metadata outside the evidence schema.
- PostgreSQL session/event/evidence ordering and participant heads are transactionally updated; event, receipt, session limits, and key metadata have database constraints. Relay restart/reconnect behavior is covered by live localhost integration tests.
